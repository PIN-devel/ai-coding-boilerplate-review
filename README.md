# 실행되는 코드와 믿을 수 있는 코드 사이 — AI 코딩 결과를 아직 무조건 신뢰할 수 없는 이유

2026년 10월 31일, 동일한 요청으로 만든 React 보일러플레이트 세 개를 비교했다. Antigravity, Cursor, Codex의 결과물은 모두 타입 검사를 포함한 빌드에 성공했다. 화면도 열렸다. 그러나 공통 HTTP 코드에서는 오류 정보를 잃거나 요청 본문을 누락하는 문제가 나왔고, 한 프로젝트는 없는 URL에서 빈 화면을 보여 주었다. ‘운영 안정성’이라는 설명과 실제로 확인한 동작 사이에는 간극이 있었다.

**AI의 결과를 신뢰하려면 결과물의 설명보다 동작의 증거를 먼저 보아야 한다.** 이번 사례는 AI가 코드를 작성하는 데 쓸모없다는 주장을 뒷받침하지 않는다. 빠르게 만들어진 결과를 검증된 기반으로 받아들이는 일이 왜 위험한지 보여 준다. 특히 보일러플레이트는 이후 기능이 반복해서 참고하는 출발점이다. 그 안의 작은 가정은 여러 기능의 기본값이 될 수 있다.

비교 대상은 [Antigravity](antigravity-test/), [Cursor](cursor-test/), [Codex](codex-test/)의 이번 결과물이다. 상세 수치와 화면 증거는 [비교 보고서](COMPARISON.md), 패키지 선택의 역사적 근거는 [React Router 조사](docs/react-router-history.md)에 정리했다. 글은 AI와 사용자의 공동 분석을 바탕으로 작성했으며, AI가 작성한 이 분석도 독립적으로 확인할 수 있도록 코드와 재현 방법을 함께 공개한다.

원본 요청은 다음과 같았다.

> vite를 사용하여 csr 개발을 위한 react 프로젝트를 만들어 줘.
> 운영 안정성을 위한 최신 lts 버전들을 검토하고, FSD 기반으로 디렉토리 구조를 만들어줘.
> 언어는 ts로 하고 기타 결정이 필요한 부분은 문의 줘.

**빌드가 성공했다는 사실은 중요하지만, 보장 범위가 제한되어 있다.**

타입 검사와 빌드는 설정된 타입 관계와 모듈 연결이 성립하는지 확인한다. 서버가 빈 응답을 보내거나 프록시가 HTML 오류 페이지를 반환했을 때의 동작까지 보장하지는 않는다. 이번 세 프로젝트가 모두 빌드에 성공했다는 사실과 아래 결함이 존재한다는 사실은 양립한다.

| 대상 | 직접 확인한 사실 | 그 사실만으로 단정할 수 없는 것 |
| --- | --- | --- |
| Antigravity | 텍스트 503 응답을 처리하다 본문을 다시 읽어 HTTP 상태 대신 TypeError가 발생 | 모든 API 오류 처리가 실패한다는 주장 |
| Antigravity | 호출자의 AbortSignal이 내부 signal로 덮어써짐 | 이것만으로 데이터 오염이나 서버 작업 취소 여부를 단정하는 것 |
| Antigravity | POST 본문 전체가 false이면 body가 누락됨 | `{ enabled: false }` 같은 객체도 누락된다는 주장 |
| Antigravity | 테마 아이콘과 html 클래스는 바뀌지만 배경색은 유지됨 | 전체 UI가 동작하지 않는다는 주장 |
| Cursor | 성공한 204 응답에서 JSON 파싱 오류가 발생 | 현재 게시글 GET 예제가 실패한다는 주장 |
| Cursor | 미일치 경로에 직접 접근하면 빈 화면이 나옴 | 전체 라우팅 구조를 다시 만들어야 한다는 주장 |
| Codex | 기본 화면·404·provider와 FSD 골격이 있고 도메인·API 구현은 거의 없음 | 발견된 결함이 적으므로 실제 서비스에서도 가장 안정적이라는 주장 |

Cursor의 lint·formatter와 기존 테스트 4개, Codex의 lint도 통과했다. 다만 Cursor의 테스트는 HTTP 성공·실패와 오류 문자열 유틸리티를 다뤘다. 통과한 검사는 그 검사에 담긴 조건을 뒷받침한다. 라우팅, 빈 응답, 취소, 실제 사용자 흐름까지 검증했다는 뜻은 아니다.

**실수가 공통 코드에 들어가면, 발견 전까지 정상적인 사용법으로 복제될 수 있다.**

Antigravity의 [HTTP 래퍼](antigravity-test/src/shared/api/client.ts)는 타임아웃과 오류 클래스를 갖췄다. 겉으로는 재사용할 준비가 된 코드다. 하지만 응답을 JSON으로 읽다가 실패하면 같은 본문을 텍스트로 다시 읽는다. 이 경로에서는 원래의 HTTP 상태가 다른 예외에 가려진다. 본문 직렬화도 값의 존재가 아니라 참·거짓 판정에 의존한다.

지금은 한곳에서 고칠 수 있다. 문제는 기능별 개발자가 공통 코드를 신뢰한 뒤, 예외가 생길 때마다 화면마다 별도 요청 함수와 catch를 추가하는 경우다. 공통 결함이 우회 코드를 낳고, 우회 코드가 서로 다른 성공·실패 해석을 만든다. 나중에는 공통 코드만 수정해도 기존 우회 처리와 충돌할 수 있다. 전파의 핵심은 줄 수보다 그 코드에 의존하게 된 가정의 수다.

Cursor의 [HTTP 함수](cursor-test/src/shared/api/http.ts)는 더 짧다. JSON을 반환하는 조회에는 충분하지만 모든 성공 응답을 JSON으로 읽는다. 이를 204를 반환하는 쓰기 API에 그대로 적용하면 서버에서는 수정이 끝났는데 화면에는 실패가 표시될 수 있다. 사용자가 다시 실행할 때의 결과는 서버의 작업 성격과 중복 방지에 달려 있다. 이것은 향후 재사용 시나리오이며 이번 프로젝트에서 중복 처리를 관측한 것은 아니다. 재시도를 안전하게 하려면 클라이언트 오류 처리와 서버의 중복 실행 방지를 함께 설계해야 한다. [Stripe의 idempotency 설명](https://docs.stripe.com/api/idempotent_requests)이 이 구분을 보여 준다.

따라서 데이터 손실을 확인하지 않은 코드를 ‘치명적’이라고 단정해서도 안 되지만, 공통 계약의 결함을 실제 쓰기 기능에 연결할 때까지 미뤄서도 안 된다. 코드 수정 비용과 이미 생긴 데이터의 복구 비용은 다르다.

**최신 기술을 검토했다는 주장도 빌드로 검증되지 않는다. React Router가 그 사례다.**

Antigravity와 Codex는 `react-router-dom@7.18.5`, Cursor는 `react-router@8.5.1`을 사용한다. v6의 공식 브라우저 예제는 `react-router-dom` 설치와 import를 안내했다. 이후 v7은 패키지를 통합했고, v8에서는 호환용 `react-router-dom`을 제거했다. [v6 튜토리얼](https://reactrouter.com/6.30.6/start/tutorial), [v8 이전 가이드](https://reactrouter.com/upgrading/v7#react-router-dom).

이번 v7 설치에서 `react-router-dom`은 실제로 동작하므로 잘못된 import 때문에 앱이 즉시 깨진다고 말할 수는 없다. 그러나 신규 프로젝트의 최신 구성을 검토해 달라는 요청에서, 이미 제거 방향이 실행된 호환용 진입점을 채택한 근거가 없다는 점은 작지 않은 누락이다. 라우팅은 링크·중첩 레이아웃·접근 제어 등으로 확장될 수 있어, 시작점의 선택이 팀의 예제와 관행에 남기 때문이다. 현재 두 프로젝트에 Router major가 중복 설치되어 충돌한다는 사실을 확인한 것은 아니며, v8 전환 전체를 단순한 import 치환으로 보장하는 것도 아니다. [자세한 연혁과 평가](docs/react-router-history.md)를 별도로 기록했다.

첫 비교 분석은 이 차이를 표에 적고도 그 의미를 충분히 평가하지 않았다. 사용자의 지적 뒤 공식 자료와 설치된 패키지를 대조해 보완했다. **코드를 생성하는 AI뿐 아니라 코드를 평가하는 AI의 설명도 검증 대상**이라는 점이 이 과정에서 다시 드러났다. 문서가 매끄럽고 결론이 단정적이라는 이유로 분석까지 신뢰해서는 안 된다.

LTS도 마찬가지다. Node의 지원 단계, Vite의 유지보수 범위, 라이브러리의 안정 버전은 같은 개념이 아니다. Node 26은 분석일 직전인 2026-10-28 LTS로 전환됐고, Codex는 더 오래 운영된 Node 24를 택한 이유를 문서화했다. 보수적인 선택 자체가 오류는 아니지만 ‘최신 LTS 채택’과는 다르다. Antigravity의 Vite 6.4도 보안 패치를 받는 범위여서 지원 종료라고 부를 수 없다. 버전 숫자의 크기만으로 안정성을 평가하지 않고 지원 정책과 선택 이유를 대조해야 한다. [Node 발표](https://nodejs.org/en/blog/release/v26.13.0), [Vite 지원 정책](https://vite.dev/releases).

**구조를 갖춘 것과 구조가 지켜지는 것도 다르다.**

Antigravity에는 FSD 레이어와 실제 기능 예제가 풍부하다. 그러나 [widgets/layout](antigravity-test/src/widgets/layout/ui/RootLayout.tsx)이 같은 레이어의 다른 slice인 header와 footer를 참조한다. [FSD 공식 규칙](https://feature-sliced.design/docs/reference/layers)은 다른 slice를 참조할 때 하위 레이어를 사용하도록 정한다. 폴더 이름이 표준과 같다는 사실만으로 의존 방향이 보장되지는 않는다.

현재 위반은 작고 수정 범위도 작다. 이를 곧바로 복구 불가능한 설계라고 부르는 것은 과장이다. 다만 같은 패턴이 복제되어 순환 의존과 역할 혼합이 늘면 분리 비용이 커질 수 있다. 반대로 Codex처럼 사용하지 않는 레이어를 비워 둔 것이 FSD 위반은 아니다. 아직 구현되지 않은 구조를 검증된 아키텍처라고 부를 수도 없다.

**운영은 피드백을 주지만, 자동으로 코드를 견고하게 만들지는 않는다.**

404, 빈 목록 안내, 테마와 같은 문제는 수정 범위가 비교적 좁다. 캐시 시간과 재조회 빈도는 실제 사용 패턴을 보며 조정하는 편이 낫다. 하지만 요청 값 보존과 성공·실패 해석처럼 여러 기능이 의존하는 계약은 기능을 확장하기 전에 확인해야 한다. 또한 취소와 재시도 정책은 적용 대상을 구분해야 한다. Query의 signal 사용은 선택적이며 Mutation은 기본적으로 오류 시 자동 재시도하지 않는다. 기본값의 존재만으로 장애를 단정할 수 없다. [Query 취소](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation), [Mutation 재시도](https://tanstack.com/query/latest/docs/framework/react/guides/mutations#retry).

발견한 현상을 재현하고, 공통 원인을 고치고, 같은 실패가 다시 나타나는지 검증할 때 운영 경험은 자산이 된다. 현상마다 예외 처리만 추가하면 운영 기간은 복잡성이 쌓인 기간이 될 수 있다. 테스트·CI·오류 기록은 결과물에 더 붙이는 장식이 아니라 이 피드백을 유지하는 수단이다. 모든 기능에 많은 테스트를 만드는 것보다, 실패하면 여러 기능의 의미를 바꾸는 경계를 먼저 검증할 필요가 있다.

**이 글의 근거 역시 제한적이다.**

이번 비교는 동일한 원본 요청으로 만들어졌다고 사용자가 설명한 결과물 세 개의 사례 연구다. 다음 한계를 전제로 읽어야 한다.

- 도구별 한 개의 결과물이다. 모델 버전, 모드, 추가 대화, 도구 권한, 생성 시간과 재시도 횟수를 통제하거나 반복 실험하지 않았다. 결과를 제품이나 모델 전체의 성능 순위로 일반화할 수 없다.
- 생성 당시 대화가 없어 ‘기타 결정은 문의’ 요구를 실제로 지켰는지는 확인하지 못했다. 추가 의존성이 있다는 사실과 동의 없이 추가했다는 판단은 다르다.
- 기능량이 다르다. 구현이 많은 결과물은 결함을 관찰할 기회도 많다. Codex의 적은 결함 수와 작은 번들만으로 더 높은 운영 안정성을 입증할 수 없다.
- 빌드는 macOS arm64, Node 24.21.0, pnpm 12.6.0에서 실행했다. Cursor의 Node 26.13.0 요구 환경과 Codex의 .nvmrc 지정 버전 24.22.2에서 검증한 결과는 아니다. 깨끗한 환경에서 설치부터 재현하는 실험도 수행하지 않았다.
- HTTP 경계 사례는 실제 Response와 대체 fetch를 사용한 격리 실행이다. 브라우저에서는 홈, 예제 조회, 검색, 테마, 미일치 경로를 확인했다. 실제 운영 서버의 쓰기 기능, 인증·권한, 배포·복구, 부하, 모바일·접근성 전수 검사와 전체 보안 감사는 하지 않았다.
- 취약점이나 데이터 유출·오염·중복 처리를 관측했다는 주장이 아니다. 비밀 파일에 대한 공개 전 점검도 모든 형태의 비밀을 탐지한다는 보장은 아니다.
- 초기 분석은 Router 선택의 의미를 놓쳤고 사용자 피드백으로 수정했다. ‘코드가 없다’는 사실과 ‘안전하다’는 판단, 발견한 오류와 미래의 피해 시나리오를 계속 구분해야 한다.
- 분석을 위해 build 산출물·캐시가 갱신됐고 Cursor의 pnpm 실행은 설치 패키지를 보충했다. 생성 직후의 완전한 디스크 스냅샷은 아니다. 공개 준비에서는 .gitignore와 문서·재현 스크립트를 추가·보완했으며 앱 소스와 의존성 선언은 수정하지 않았다.

이 조건에서 가능한 결론은 제한적이지만 분명하다. 이번 결과물들은 빠르게 작동하는 출발점을 제공했다. 동시에 정상 경로의 성공, 구조의 외형, 안정성을 강조하는 설명만으로는 확인되지 않는 결함과 선택의 누락도 남겼다. **AI가 만든 코드를 채택할 때 필요한 신뢰는 사용한 도구의 이름이나 설명의 자신감이 아니라, 요구사항·현재 문서·실패 사례와 대조한 증거에 비례해야 한다.**

**직접 확인하기**

세 프로젝트는 독립적인 pnpm 프로젝트다. 각 폴더의 Node 요구 사항과 README를 확인한 뒤 해당 폴더에서 `pnpm install --frozen-lockfile`, `pnpm build`를 실행한다. 루트에는 별도의 workspace나 통합 설치 설정이 없다.

Antigravity의 의존성을 설치한 뒤 루트에서 다음 명령으로 HTTP 관련 네 가지 관측을 재현할 수 있다. 서버 요청 없이 실행하며 프로젝트의 .env도 읽지 않는다.

```sh
node scripts/reproduce-findings.mjs
```

이 명령의 성공은 **기록한 결함이 재현되었다는 뜻**이다. 제품의 정상 동작이나 운영 준비 완료를 뜻하지 않는다. 결함을 수정한 뒤에는 관측 결과와 문서도 갱신해야 한다. 다른 프로젝트의 검사 명령과 수치·화면은 [비교 보고서](COMPARISON.md)를 참고한다.

공개를 준비하며 루트와 세 프로젝트의 .gitignore에 환경변수 파일, 설치·빌드·캐시·테스트 산출물과 로컬 도구 설정의 제외 규칙을 보완했다. 공개 가능한 `.env.example`과 재현성을 위한 lockfile은 남겼다. gitignore는 이미 추적된 파일을 제거하거나 비밀 유출을 복구하지 않으며, `VITE_` 변수도 비밀 저장소가 아니다. 이 저장소에는 확인한 결함을 분석 대상으로 남겼으므로 운영용 템플릿으로 그대로 복제하기 전에 위 계약부터 검토해야 한다.
